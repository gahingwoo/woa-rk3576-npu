# M2: driver skeleton and test tool

Exit criterion: **the device starts with no problem code, and the version
register the driver reads matches the one the firmware logged.**

Nothing in M2 has run on a board yet. CI builds the driver and the tool for
ARM64 and test-signs them. The tool's `selftest` runs on Linux in CI. None of
that is a hardware result.

## What is in it

| Path | What |
|---|---|
| [`drivers/rknpu`](../drivers/rknpu) | `rknpu.sys`, KMDF, binds `ACPI\RKCP3576` |
| [`include/rknpu_ioctl.h`](../include/rknpu_ioctl.h) | the IOCTL interface, shared with the tool and, from M4, charsiu |
| [`tools/rknputest`](../tools/rknputest) | `rknputest info`, `rknputest regs <off> <n>`, `rknputest selftest` |
| [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) | Linux selftest; WDK build, test signing, artifact `rknpu-m2-arm64` |

The driver:

- maps the 64 KiB register window from `_CRS` (both cores; core 1 at +0x8000);
- connects both interrupts, GSIV 279 (core 0 and its IOMMU) and 280 (core 1
  and its IOMMU). The ISR acks what it finds and the DPC counts. M2 starts no
  job, so both counts should stay 0;
- creates `\\.\RKNPU`, for administrators and SYSTEM only, one handle at a time:
  - `GET_INFO`: both cores' PC version registers and interrupt state, the four
    IOMMU status words, the interrupt counters, and the PMU and CRU state of
    the NPU (domains, gates, `clk_rknn_dsu0`). The PMU and CRU are not in
    `_CRS`, so the driver maps one page of each read-only;
  - `READ_REGS`: reads up to 1024 words, but only inside a block the device
    tree describes (pc, cna, the two IOMMU instances, core). Anything else in
    the window is refused, because a read that decodes to nothing can be an
    SError on this SoC;
- does nothing to power, clocks or resets, in D0 entry or anywhere else. The
  firmware owns all of it. The only register writes are to each core's PC
  interrupt mask and clear (at D0 entry and in the ISR), plus an IOMMU
  `INT_CLEAR` if an IOMMU interrupt ever arrives. `GLOBAL_OPERATION_ENABLE`
  is never written. If the PMU and CRU show the NPU unpowered at D0 entry, the
  start fails (code 10) instead of reading the NPU.

The function codes 0x810 to 0x81F are reserved for M3 (buffers, submission,
wait, reset). The driver answers them with `STATUS_INVALID_DEVICE_REQUEST`.

## Board test

Board: the LCKFB TaishanPi 3M. It is the only board where the firmware shows
the NPU option, because the option needs I2C access to the RK806. Windows 11
23H2 with test signing on (`bcdedit /set testsigning on`, as for the
woa-rk3576 drivers).

### 0. Firmware

Use edk2-rk3576 branch `npu-acpi`. In setup, open *ACPI / Device Tree*: the
config table mode must include ACPI. Set *NPU (experimental)* to Enabled,
save and reset. The serial log should then show these lines, in this order:

```
RK3576Dxe: NPU: vdd_npu_s0 (BUCK2) 800000 uV, on
RK3576Dxe: NPU: powered, STATUS0=0x........ REPAIR0=0x........ IDLE0=0x........
RK3576Dxe: NPU: core 0 version=0x........ version_num=0x........ mmu status=0x........./0x........
RK3576Dxe: NPU: core 1 version=0x........ version_num=0x........ mmu status=0x........./0x........
```

Write down both `core` lines; step 3 compares them with what the driver
reads. In the UEFI shell, `acpiview -s SSDT` should list a table with OEM
table ID `RKNPU`. If the log says `rail not confirmed, NPU left off` or a
domain `did not come up`, stop there: the device will not exist, and that is
an M1 problem.

### 1. Install

Get the artifact `rknpu-m2-arm64` from the CI run of the commit under test.
It contains `rknpu\` (`rknpu.sys`, `rknpu.inf`, `rknpu.cat`), `rknputest.exe`
and `signer.cer`. The signing certificate is made fresh in each run, so
always use the `signer.cer` from the same artifact as the driver.

As administrator, after `w32tm /resync /force` (a wrong clock makes the
signature look not yet valid):

```
certutil -addstore -f Root signer.cer
certutil -addstore -f TrustedPublisher signer.cer
pnputil /add-driver rknpu\rknpu.inf /install
```

### 2. Device Manager

*System devices*: "Rockchip RK3576 NPU (RKNN, bring-up)", no yellow mark, and
*Device status* "This device is working properly". From a prompt:

```
pnputil /enum-devices /instanceid "ACPI\RKCP3576\0" /drivers
```

should show `Status: Started` and `Driver Name: oem<N>.inf` (`rknpu.inf`).

If the firmware option is off, the device does not exist and the driver
binds nothing. That is not a failure of M2.

### 3. `rknputest info`

As administrator:

```
rknputest info
```

Expected shape, with the `0x........` values filled in by the hardware:

```
interface 1 (this tool 1), struct 424 bytes, flags 0x00000007 interrupts clocks domains-on
registers 0x27700000 + 0x10000, 2 cores
core 0: version=0x........ version_num=0x........
  pc: operation_enable 0x........ int mask 0x00000000 status 0x00000000 raw 0x........ task_con 0x........ task_status 0x........
  mmu 0: status 0x........ (paging off) dte 0x........ int_rawstat 0x........ int_mask 0x........
  mmu 1: status 0x........ (paging off) dte 0x........ int_rawstat 0x........ int_mask 0x........
  irq: gsiv 279, isr 0 (unclaimed 0), dpc 0, last pc 0x00000000, last mmu 0x00000000/0x00000000 fault 0x00000000/0x00000000
core 1: ... gsiv 280 ...
pmu: STATUS0 0x........ REPAIR0 0x........
cru: CLKSEL86 0x........ GATE28 0x........ GATE29 0x........ GATE31 0x........ GATE32 0x........
clk: gpll 1188000000 Hz, clk_rknn_dsu0 594000000 Hz
checks:
  [ok] driver and tool agree on the interface
  [ok] register window is 64 KiB
  [ok] interrupts connected
  [ok] NPU domains on and clocks ungated
  [ok] core 0 version register reads a value (not 0, not all ones)
  [ok] core 0 IOMMUs have paging off
  [ok] core 0 interrupt is GSIV 279
  [ok] core 0 no interrupt seen (no job was started)
  ... the same four for core 1 ...
  [ok] clk_rknn_dsu0 is 594 MHz (GPLL / 2)
  [ok] both cores report the same version
compare by hand with the firmware serial log:
  RK3576Dxe: NPU: core 0 version=0x........ version_num=0x........ mmu status=0x......../0x........
  RK3576Dxe: NPU: core 1 version=0x........ version_num=0x........ mmu status=0x......../0x........
RKNPU INFO: OK
```

Exit status: 0 when every check passes, 2 when one fails, 1 when the device
cannot be opened.

**M2 passes** when step 2 shows the device started with no problem code, and
the two `compare by hand` lines equal the firmware's two `core` lines from
step 0, character for character. The tool cannot check that part itself,
because the firmware log never reaches Windows.

Two things to read with care:

- The `gsiv` check depends on what Windows puts in the raw resource list. 279
  and 280 are what the SSDT asks for. A different number with the device
  started and no interrupt storm is a question about that field, not a
  failure.
- The `clocks` flag needs `MmMapIoSpaceEx` to map the PMU and CRU pages
  read-only. If it is clear, the clock lines are missing and their check is
  skipped. The device still starts; say so in the report.

### 4. A few register reads

```
rknputest regs 0x0 16
rknputest regs 0x8000 16
rknputest regs 0x2000 8
rknputest regs 0xa100 8
```

The first word of the first two dumps is each core's version register again.
`rknputest regs 0x4000 1` must be refused by the tool, before it reaches the
driver.

### 5. Leave it

Reboot once with the driver installed and repeat steps 2 and 3. Then the
driver can stay installed: with the firmware option off it binds nothing.

## What to send back

- the firmware serial log from power-on to the boot manager (step 0);
- the `pnputil /enum-devices` output (step 2), or the problem code shown;
- `rknputest info` and the four `regs` dumps, from both boots;
- on failure, the `C:\Windows\INF\setupapi.dev.log` lines around `RKCP3576`.

## Not tested

- Nothing here has run on a board: not the driver, the tool, or the INF.
- The firmware side (`npu-acpi`) has not run on hardware either, so step 0 is
  also its first run.
- Whether Windows reports the GSIV in the raw interrupt descriptor as the
  driver assumes.
- Whether `MmMapIoSpaceEx` accepts `PAGE_READONLY` for the PMU and CRU pages.
- The ISR and DPC paths: with no job started they should never run. M3 is the
  first time they do work.
