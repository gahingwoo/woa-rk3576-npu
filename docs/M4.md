# M4: charsiu on Windows

Exit criterion: **Llama-3.2-1B, greedy, gives the same text through rknpu.sys
under Windows as through rocket under Linux, on the same board, from the same
charsiu commit.**

Nothing in M4 has run on a board yet. What has run, on a Linux desk and in CI,
is listed under "What is already checked"; none of it is a hardware result.

## Design

### The device layer

charsiu talks to the kernel through one file, `src/device.c`, and four rocket
ioctls. `device_rknpu.c` keeps its interface and maps it onto the M3 IOCTLs:

| charsiu | rocket (Linux) | here |
|---|---|---|
| `charsiu_open` | one fd, one scheduler entity | one handle to `\\.\RKNPU`; charsiu opens two (one a core) |
| `charsiu_bo_alloc` | CREATE_BO + mmap, IOVA per fd | CREATE_BO + MAP_BO, physical address below 4 GiB, write-combined |
| `charsiu_bo_prep` | wait for the BO's fences, invalidate the cache | wait for the device's last job (a superset of the BO's fences); no cache to invalidate |
| `charsiu_bo_fini` | clean the cache | `DSB SY`, so the write-combine buffer has drained |
| `charsiu_submit_jobs` | N jobs, queued on the entity | their tasks in order, as SUBMITs of at most 64 tasks and 256 KiB of stream, each after the last finished, on whichever core is free |
| `charsiu_bo_free` | GEM_CLOSE | FREE_BO after the device's last job |

A device's jobs never overlap, which is what rocket's entity does too, so
running them back to back changes no result. Waiting for more than a BO's own
fences is never wrong, only slower; that is M5's business. The two devices
run concurrently, one on each core, as on Linux.

### Driver changes (M4 section of rknpu_ioctl.h)

All behind flags; an M3 caller sees the M3 driver, and `rknputest m3` is run
again in the board test to prove it.

- **SUBMIT with `RKNPU_SUBMIT_COPY`.** charsiu writes its streams through the
  buffer's mapping, so M3's rule (a stream's buffer may not be mapped) cannot
  hold. The driver copies each stream into a per-core **copy arena** (256 KiB,
  contiguous, below 4 GiB, never mapped into a process), checks the copy and
  points the PC at it. What runs is what was checked. charsiu's largest SUBMIT
  is 16 streams of 148 entries, 18944 bytes.
- **The check now has a register list.** Besides refusing the PC block and
  any address register pointing outside the caller's buffers, SUBMIT refuses
  any register charsiu never writes. The list (147 block/register pairs) is
  generated from charsiu's emitter by `m3gen regs` over 576 jobs (all weight
  and activation types, 1 to 80 rows, both CBUF windows); CI regenerates it
  and fails on a difference, and checks that the registers that move with a
  buffer are exactly the five address registers. A whole Llama-3.2-1B run on
  the in-memory driver (prefill, decode, fp16 attention) writes exactly the
  same 147, and with every buffer placed at two different bases only those
  five carry addresses. So every address a stream can program is one of the
  five, and each is checked; the IOMMU registers, for example, cannot be
  written. Sizes are still not checked (the NPU can read or write past the
  start of a buffer by as much as the stream's size registers say), so this is
  still not a sandbox and the device stays administrators-only.
  `Device Parameters\M4AllowUnlisted` = 1 (read at device start) lets
  unlisted registers through, logged: the back-out if the board finds a path
  the list missed, not a mode to run in.
- With copies, MAP_BO and WRITE_BO are refused only while an M3-style job
  runs, and FREE_BO only while a job of the **same handle** runs.
- **WAIT with `RKNPU_WAIT_POLL`** returns `RKNPU_JOB_RUNNING` and stops nothing
  (charsiu polls for 200 us before blocking, as on Linux).
- A finished job stays answerable for 32 jobs: WAIT finds it in a history
  even after another handle's job took its core.
- `RKNPU_BO_MAX_TOTAL` is 1 GiB (M3: 512 MiB).
- Breadcrumbs: two new stages, 10 = a stream refused (`M3Value1` = entry
  index, `M3Value2` = block << 16 | register) and 11 = a core's arena
  allocated (size, address). Buffer stages now write only the first 32 of
  each kind and then every 256th (charsiu makes about 1300 buffers, and each
  crumb is a registry flush on eMMC). Job crumbs are charsiu's choice:
  `device_rknpu.c` asks for them on the first 16 SUBMITs of each device and
  every 4096th after (`CHARSIU_RKNPU_CRUMBS=all` for every one, `off` for
  none). A timeout or a refusal always writes.

### Same text: the CPU side

Only the matmuls go to the NPU; norms, RoPE, softmax and the rest stay on the
CPU, so the CPU arithmetic has to agree too.

- **Compiler.** charsiu's Linux build is gcc `-std=c11`, which does not
  contract `a*b+c` into an fma; the Windows build is clang with
  `-ffp-contract=off`. Built both ways on the desk (aarch64 Linux), the CPU
  path gives byte-identical text for 64 and 128 tokens, at 2 and 4 threads.
- **libm.** UCRT's `expf` is not glibc's, and a last-bit difference in a
  softmax can flip a greedy token. The Windows exes carry glibc's own
  `expf`/`sinf`/`cosf`/`powf` (glibc took them from ARM optimized-routines),
  built with fma contraction as glibc builds them. CI checks them against
  arm64 glibc on every one of the 2^32 float inputs (expf, sinf, cosf: 0
  differ) and on the RoPE inputs plus 2*10^8 random pairs (powf: 0 differ),
  and fails the build if an exe imports any of the four from the CRT. Without
  fma contraction, 34 sinf/cosf inputs differ; that is why it is on. Llama
  uses no other libm function on its path (`tanhf` is gemma's, `exp`/`log`/
  `pow` are the AWQ option's).
- **Files and output in binary mode**, so the model, `long.txt` and stdout are
  the same bytes as on Linux.
- 16 MiB of stack per thread (Linux gives 8; Windows' default is 1).

### Memory, and the 4 GB board

Measured on the in-memory driver, which allocates exactly what the driver
would:

| Run | NPU buffers | Largest |
|---|---|---|
| short prompt, `-c 512` (the M4 arm) | 1314, 701 MiB | 4.0 MiB |
| 1176-token prompt, `-c 2048` | 1590, 791 MiB | 5.5 MiB |
| int8 weights (`CHARSIU_NPU_W4V=0`), for comparison | 1590, 1379 MiB | 8.0 MiB |

Every buffer is physically contiguous and below 4 GiB, but none is larger
than 5.5 MiB: the need is about 0.7 GiB in pieces of at most a few MiB, not
one block. On a 4 GB RK3576 board the DRAM below 4 GiB is 0x40000000 to
0xF0000000 (2.75 GiB), shared with everything Windows keeps low. Add the
process itself: the 1.3 GB model file mapped (file-backed pages, which Windows
can drop once the weights are staged) and about 0.6 GB of heap (KV cache,
activations, staging copies). That is tight but realistic right after a boot;
it is not realistic for int8 weights, which the 1 GiB cap refuses anyway.

If a CREATE_BO fails, charsiu says so (`rknpu buffer of N bytes failed (-12)
... no contiguous memory below 4 GiB`) and keeps that tensor on the CPU, so
the text can then differ. In order: reboot and run first; the Q4_0 file
(773 MB instead of 1.3 GB of page cache; the NPU weights are requantised to
int4 either way, so the buffers are the same, but the Linux reference must
then use Q4_0 too); then M6 (the driver maps the NPU IOMMU, so buffers can be
scattered and above 4 GiB). Chunking buffers further would not help: they are
already small.

## What is already checked (desk and CI, not hardware)

- `make -C port check`: the device layer on the in-memory driver: 100 tasks
  go as 64 + 36; long streams split by arena bytes; a device whose core is busy
  takes the other; a WAIT after another handle took the core; a stream with an
  address outside its buffers, in another device's buffer, writing the PC
  block, or writing an IOMMU register is refused, and the device works after.
- `m3gen check`: the list, the five address registers, the M3 streams.
- A whole Llama-3.2-1B-Instruct-Q8_0 run (desk only: the weights are not in
  CI) on the in-memory driver with the shipped NPU settings: 0 refusals,
  5390 SUBMITs, at most 16 tasks and 18944 bytes a SUBMIT, fp16 attention on
  all 240 layer calls.
- `libm-check` (above), on `ubuntu-24.04-arm` in CI.
- The exes are ARM64 PE files that import only UCRT and kernel32. They have
  never been started: there is no ARM64 Windows in CI.

The driver's M4 paths build in CI and have never run.

## Board test (one shot, both operating systems)

Board: TaishanPi 3M, firmware with `AcpiNpu` = 1. Part A under Armbian (the
M0 setup: Armbian 7.3.5 edge with rocket, Armbian's DTB through GRUB's
`devicetree` line, because the firmware's TSPI DTB has the NPU disabled; no
`iomem`, `passthrough` or `mem=` option needed). Part B under Windows 11
23H2 with test signing, the M3 driver installed. One CI run provides both
artifacts: `rknpu-m4-arm64` (driver, rknputest) and `charsiu-m4-arm64`
(the Windows exes, `linux/charsiu_run` and `linux/charsiu_matmul`, the
scripts, `long.txt`, this file).

### 0. The model (fetch it, never commit or ship it)

accept by downloading it. Fetch it on a machine with room, like the other
blobs this project uses:

```

  https://huggingface.co/unsloth/Llama-3.2-1B-Instruct-GGUF/resolve/main/Llama-3.2-1B-Instruct-Q8_0.gguf
```

### A. Linux reference (as root, under Armbian)

```
ls /dev/accel/                       # accel0 (rocket is up)
unzip charsiu-m4-arm64.zip -d charsiu-m4 && cd charsiu-m4
chmod +x linux/* ./*.sh              # a GitHub artifact zip drops the exec bits
./linux-ref.sh /mnt/stick/Llama-3.2-1B-Instruct-Q8_0.gguf
```

About five minutes. Seven arms, each greedy, `-t 4`, with a clean `CHARSIU_*`
environment; the NPU arms set exactly what `charsiu-runner` sets
(`CHARSIU_NPU=1 CHARSIU_NPU_QUANT=1 CHARSIU_NPU_W4V=1 CHARSIU_NPU_KMAX=1024
CHARSIU_NPU_W4_GROUP=1024 CHARSIU_NPU_MAXN=262144 CHARSIU_COEF_ELEMS=65536`):

| Arm | Arguments | Why |
|---|---|---|
| short-cpu | `-p "Write a short story about a lighthouse keeper who finds a message in a bottle." -n 128 -c 512` | the control: no NPU |
| short-npu, short-npu2 | the same, NPU | the comparison, twice: Linux must repeat itself |
| long-cpu, long-npu | `-f long.txt -n 64 -c 1024` (515 prompt tokens) | batched prefill and fp16 attention, which a short prompt never reaches |
| logits-cpu, logits-npu | short prompt, `--logits 10` | the ten top logits after the prompt, to six decimals |

Plus `charsiu_matmul 1 256 64` (M0's job, to compare byte for byte). It ends
with the `.text` MD5s (stdout without the timing lines that start with `[`),
`the NPU arm repeats itself byte for byte`, and `m4-linux.tar.gz`. Keep that
file. The CPU arms do not depend on the board; on the desk the same binary
gives:

```
a0e97e1ad98c246829f485bb0d95d2eb  ./short-cpu.text
40155508dcf235caf4a1459bb1dc4a5d  ./long-cpu.text
3fc96be43fcee59bbf6b1270f9c6e5a6  ./logits-cpu.text
```

If the board's differ, stop: the comparison below would not mean anything.
If the NPU arm does not repeat itself, M4's criterion is not testable as
written; send everything.

### B1. Install the M4 driver (Windows)

Exactly as M3's steps 1 and 2 ([M3.md](M3.md)), with `rknpu-m4-arm64`:
stage with `pnputil /add-driver` (no `/install`), mark for reinstall with
`rknpu-reinstall.ps1` as SYSTEM, reboot. Then:

```
pnputil /enum-devices /instanceid "ACPI\RKCP3576\0" /drivers
rknputest info
```

`Status: Started`, every M2 check passes, and a new line
`m4: version 1, copy arena 256 KiB a core, buffers up to 65536 KiB each and 1024 MiB in all`.

### B2. Run it

Copy `m4-linux.tar.gz` over and unpack it (`tar xf` works on Windows 11),
put `rknputest.exe` from `rknpu-m4-arm64` beside the scripts, then as
administrator:

```
powershell -NoProfile -ExecutionPolicy Bypass -File win-run.ps1 -Model E:\Llama-3.2-1B-Instruct-Q8_0.gguf -Linux .\m4-linux
```

In order, stopping early where it says so: `rknputest info`; `rknputest m3`
(the M3 ladder must still pass on the M4 driver: the old path plus the new
register list); `charsiu_matmul 1 256 64` (the first copied SUBMIT, one job);
then the seven arms, with the breadcrumbs saved after each. The NPU arms set
`CHARSIU_RKNPU_STATS=1`, so each `.err` ends with one counter line per
device (submits, waits, busy retries, timeouts, DMA errors, refusals, peak
buffers and MiB). It ends with:

```
short-cpu: SAME
short-npu: SAME
long-cpu: SAME
long-npu: SAME
logits-cpu: SAME
logits-npu: SAME
M4 COMPARE: SAME TEXT
win-run: done, send .\m4-windows.zip
```

**M4 passes** with `short-npu` and `long-npu` SAME, the `*-npu.err` files
showing 0 timeouts, 0 DMA errors, 0 refused and no `buffer ... failed` line,
and `rknputest info` afterwards with no unclaimed interrupts.

How to read the rest:

| Result | Reading |
|---|---|
| `*-cpu` DIFFERENT | the port's CPU side (compiler, libm, compat), not the NPU; compare the MD5 with the desk's above |
| `logits-npu` SAME, `short-npu` DIFFERENT | cannot happen if both are greedy over the same logits; send everything |
| `*-npu` DIFFERENT, logits close | the NPU computed differently somewhere; `matmul.txt` against the Linux one says whether a single job already does |
| `buffer of N bytes failed (-12)` in an `.err` | memory below 4 GiB ran out (see Memory); rerun right after a reboot |
| `SUBMIT ... failed: -13` | a stream refused; the crumbs (`M3Stage` 10, `M3Value2` = block << 16 \| register) and DbgView name it. If it is a register the list missed, `M4AllowUnlisted` (back-out) and send it |
| `TIMED OUT` | as M3's table; the driver reset the core and charsiu carried on |
| `charsiu: died in ...` | the crash note: the last stage charsiu recorded |
| the board goes down | reboot and send `reg query "HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\RKCP3576\0\Device Parameters"`: the crumbs were flushed before the job; this board writes no minidumps |

Options: `-SkipM3`, `-NpuOnly` (skip the CPU arms, which take minutes),
`-Out DIR`. On the desk, `tools/m4/compare.sh m4-linux m4-windows` repeats
the comparison.

### Back-out

- `M4AllowUnlisted`: `reg add "HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\RKCP3576\0\Device Parameters" /v M4AllowUnlisted /t REG_DWORD /d 1 /f`
  as SYSTEM (the M3 scheduled-task trick), then restart the device or reboot;
  delete the value to undo.
- Back to M3: firmware option off, boot, `pnputil /delete-driver oem<N>.inf`
  for the M4 `rknpu.inf`, option on, reboot (M3.md's back-out, one step later).
- Quickest: `AcpiNpu` = 0 in the UEFI shell, as in M3.md.
- charsiu itself installs nothing: delete the directory.

## What to send back

`m4-linux.tar.gz`, `m4-windows.zip` (it holds every output, `.err` file,
crumb dump and `rknputest` output), and the two `pnputil` outputs.

## Risks and what is not tested

- **Nothing here has run on hardware**: not the copy arena, the register
  list, the job history, the poll, or any charsiu exe on Windows at all.
- **Memory below 4 GiB** (above): about 0.7 GiB of contiguous pieces plus a
  1.3 GB mapped model on a 4 GB board.
- **CPU reads of NPU output are uncached** (write-combined mappings, as in
  M3), and charsiu reads its int32 accumulators back on every call. Decode
  will be slower than on Linux; correctness does not depend on it. Cached
  buffers with PREP/FINI cache maintenance are M5.
- The driver validates with a linear search over the handle's ~650 buffers
  (one cache entry in front); some microseconds a SUBMIT. M5.
- Every SUBMIT waits for the device's previous one, and a job of more than 64
  tasks is split with a wait in between; rocket queues instead. Correct,
  slower. M5.
- `npudev.c` line 6430 reads an uninitialised pointer (`e->t`) in an argument
  that `w4_for()` ignores; at `-O2` both gcc and clang drop the load. Upstream
  charsiu should fix it; the port does not change charsiu.
- A prompt or path with non-ASCII characters goes through the ANSI code page
  on Windows; the test uses ASCII only.
- Only the shipped NPU settings and Llama-3.2-1B are covered. Another model or
  experiment switch may reach a register off the list (refused, loudly).
