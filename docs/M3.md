# M3: buffers, submission, interrupts

Exit criterion: **an int8 GEMM run on the NPU under Windows gives exactly the
CPU's result, on both cores, small and medium.**

Nothing in M3 has run on a board yet. CI builds the driver and the tool, runs
`rknputest m3` on Linux against an in-memory stand-in for the driver, and
checks the GEMM's register streams and packing byte for byte against charsiu.
None of that is a hardware result.

## Design

### Nothing new runs until rknputest m3 asks

Every M3 path sits behind a new function code (0x810 on). `GET_INFO` and
`READ_REGS` behave as in M2. With the M3 driver installed and only
`rknputest info` ever run, the driver allocates no buffer, writes no job
register, runs no `_DSM` and writes nothing to the registry. The changes on
the always-run paths are small: D0 entry also records each core's version
register (a read), DeviceAdd creates two wait locks and opens the device's
`Device Parameters` key, and the ISR first asks m3.c whether a job owns the
interrupt (no job, no register access there).

### Buffers and the IOMMU

What the firmware leaves: edk2-rk3576 `Npu.c` powers the domains and sets the
clock, and never touches the four NPU IOMMU instances. They are in reset
state: `STATUS` 0x18 (idle, replay buffer empty, paging off) and `DTE_ADDR`
0, logged by the firmware and read again under Windows in M2. With paging off
the IOMMU passes addresses through, so the NPU address of a buffer is its
physical address.

M3 keeps it that way (the plan's IOMMU bypass, FEASIBILITY.md). The driver
never writes an IOMMU register except `INT_CLEAR` in the ISR, as in M2, and
SUBMIT refuses a core whose IOMMU shows paging on.

- `CREATE_BO`: `MmAllocateContiguousNodeMemory`, below 4 GiB, zeroed,
  `PAGE_WRITECOMBINE` (Normal non-cacheable on ARM64). The NPU is not cache
  coherent (`_CCA 0`), and with a non-cacheable mapping there is no cache to
  maintain, so rocket's `PREP_BO`/`FINI_BO` have no M3 counterpart (their
  codes stay reserved for cached buffers in M5). The same model as the
  vdpu383 driver in woa-rk3576. Limits: 64 MiB a buffer, 512 MiB in all.
- `WRITE_BO` / `READ_BO`: copies through the driver (direct I/O). rknputest
  uses only these, so by default no NPU page is ever mapped into a process.
- `MAP_BO` / `UNMAP_BO`: optional (`rknputest m3 --map`), a write-combined
  user mapping of the same pages, so no page ever has two cache attributes.
- `FREE_BO`, and every buffer of a handle when it closes. A job still running
  is waited for (500 ms), stopped and its core reset before any buffer it may
  be writing is freed.

### Submission, completion, timeout, reset

SUBMIT copies rocket's `rocket_job_hw_submit()` (drivers/accel/rocket/
rocket_job.c) write for write, with the RK3576 `PC_TASK_CON` layout of the
RK3576 series (v17): `BASE_ADDRESS` 1, CNA and CORE `S_POINTER` with the
per-core extra bit, `BASE_ADDRESS`, `REGISTER_AMOUNTS` ((count + 1) / 2 - 1),
`INTERRUPT_MASK` and `CLEAR` = DPU_0 | DPU_1, `TASK_CON`, `TASK_DMA_BASE_ADDR`
0, `OPERATION_ENABLE` 1. A job is up to 64 tasks; the ISR starts each next
task itself, as `rocket_job_next_locked()` does. One job per core at a time.

The ISR does what `rocket_job_irq_handler()` and `rocket_job_handle_irq()` do:
it keys on `INTERRUPT_RAW_STATUS` DPU bits, writes `INTERRUPT_MASK` 0,
`OPERATION_ENABLE` 0, `INTERRUPT_CLEAR` 0x1ffff, records the status, and either
starts the next task or marks the job finished. The DPC sets the job's event.
DMA read or write error bits end the job with `RKNPU_JOB_DMA_ERROR`.

WAIT waits on that event at PASSIVE_LEVEL (default 500 ms, rocket's
`JOB_TIMEOUT_MS`; rknputest uses 2000). On timeout it does what
`rocket_reset()` does: under the interrupt lock, mask, stop and clear; then
`KeFlushQueuedDpcs()` (the `synchronize_irq()` here); then the core's soft
reset through the SSDT's `_DSM` function 1 (SRST_A_RKNN0 or 1 for 10 us,
`rocket_core_reset()`; RK3576 has one reset per core). The driver never
writes the CRU itself. RESET runs the same `_DSM` on an idle core.

Locking: every wait (the job event, the `_DSM` call, a registry flush)
happens at PASSIVE_LEVEL holding only wait locks. The interrupt spin lock is
held for a few register writes and bookkeeping and never across a wait; the
DPC takes nothing but that lock, briefly, and sets an event. This is the rule
the woa-rk3576 Bluetooth driver broke when it hit `DPC_WATCHDOG_VIOLATION`.

### The stream check

With paging off nothing stands between a register stream and physical
memory. A wrong address in a stream is a DMA write into memory Windows owns,
which shows up later as an unrelated bugcheck (`MEMORY_MANAGEMENT`, pool
corruption) far from its cause. SUBMIT therefore reads every stream before
starting it and refuses (`STATUS_ACCESS_VIOLATION`) one that:

- writes the PC block (register offset below 0x1000), which could chain to a
  stream the driver never saw; or
- puts an address outside the caller's buffers into one of the address
  registers in `rknpu_regcmd.h`: CNA 0x1088 (input), 0x1110 (weights),
  DPU 0x4018 (output), RDMA 0x5020 and 0x5024 (coefficients).

That list is what charsiu's int8 stream uses, found by m3gen by moving each
buffer and seeing which entries move (CI repeats it). It is not every address
register RK3576 has, so this catches a wrong address from rknputest or
charsiu, not a hostile stream. The device stays administrators-only. A
stream's buffer may not be user-mapped at SUBMIT, and MAP_BO is refused while
a job runs, so a checked stream cannot change before the NPU reads it.

### Breadcrumbs

At each stage the driver writes six DWORDs under
`HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\RKCP3576\0\Device Parameters` and
calls `ZwFlushKey`: `M3Stage`, `M3Seq`, `M3Core`, `M3Value1`, `M3Value2`,
`M3Count`. Stages (`RKNPU_CRUMB_*`): 1 buffer created (size, address),
2 mapped, 3 submitted (stream address, entries; flushed before
`OPERATION_ENABLE`), 4 interrupt seen (interrupts, tasks done), 5 WAIT
returned (raw status, task status), 6 timed out, 7 reset returned (NTSTATUS,
version after), 8 unmapped, 9 freed. If the board goes down, the last stage
on disk says where. rknputest turns crumbs off after the first run of each
shape (`RKNPU_SUBMIT_NO_CRUMBS`) so the timings do not include disk flushes;
a timeout always writes them.

### The GEMM

`m3_gemm.h` explains it in full. In short, per task one row:
`C[c] = sum_i (A[i] - 128) * (B[c][i] - 128)`, int8 operands, the raw int32
accumulator (charsiu's `acc_out`). It is charsiu's `tools/npu_gemm_test.c`
M = 1 control, the shape charsiu's lab notebook records as exact on the board
under Linux. A GEMM with M rows is M tasks in one job (same weights and
coefficients, one input and one output row each), which also exercises the
ISR's task chaining. M > 1 inside one task is not used: charsiu has never had
the `acc_out` path right above one row.

- The streams (143 entries) are `charsiu_emit_job()` output, captured by
  `tools/m3gen` with the addresses taken out (`m3_streams.h`, generated; CI
  regenerates it and fails on any difference).
- The weight and input packing and the coefficient buffer are formulas in
  `m3_gemm.h`; `m3gen check` compares them byte for byte with
  `charsiu_pack_weights()`, `charsiu_pack_input()` and
  `charsiu_build_coefs()` on 13 shapes, in CI.
- The test data are npu_gemm_test's (`mix()`), and so is the reference.

Ladder, per core, stopping at the first failure:

| Step | M x K x N | Why |
|---|---|---|
| 1 | 1 x 64 x 64 | charsiu's board-exact shape |
| 2 | 4 x 256 x 64 | npu_gemm_test's and m0_bypass's K and N; 4 tasks in one job |
| 3 | 8 x 256 x 256 | |
| 4 | 16 x 1024 x 1024 | medium: 1 MiB of weights, read by each of 16 tasks |

Each output row is followed by 4 KiB of canary (0xA5A5A5A5); a changed
canary word is reported as an overrun. Then each core is reset through RESET
and step 1 runs again on it.

## Run M0 under Linux first?

Yes, if a kernel with rocket and the RK3576 NPU series can be booted on the
board ([tools/m0](../tools/m0/README.md), steps 1 to 6). `m0_bypass` submits
the same charsiu stream (m = 1, K = 256, N = 64, 143 entries) with the IOMMU
not translating, so it answers the one question M3 cannot separate from its
own bugs: does the NPU work in bypass at all. A pass there means a Windows
failure is the driver's. A failure there means do not run M3; M6 (the driver
owns the IOMMU) comes first.

If no such kernel is at hand (Armbian edge 7.3.4 has no rocket), M3 can go
first. Its failure modes are bounded the same way (timeout, then reset;
DMA error; wrong numbers), but then "bypass does not work" and "the driver is
wrong" look the same, and the first job is also the first bypass job ever run.

## Board test (one shot)

Board: TaishanPi 3M, Windows 11 23H2, test signing on, firmware with
`AcpiNpu` = 1 (as in M2), the M2 driver installed and started.

Because an unexplained `MEMORY_MANAGEMENT` bugcheck is under investigation on
this board, do this right after a clean boot, write down whether that
bugcheck has happened on this install before, and keep minidumps on
(`C:\Windows\Minidump`). A bugcheck after `rknputest m3` is not by itself
proof that M3 caused it; the breadcrumbs and the dump decide.

### 1. Stage the package (do not install it on the running device)

Artifact `rknpu-m3-arm64` from the CI run of the commit under test:
`rknpu\` (`rknpu.sys`, `rknpu.inf`, `rknpu.cat`), `rknputest.exe`,
`signer.cer`, `rknpu-reinstall.ps1`, `M2.md`, `M3.md`. As administrator, after `w32tm /resync /force`:

```
certutil -addstore -f Root signer.cer
certutil -addstore -f TrustedPublisher signer.cer
pnputil /add-driver rknpu\rknpu.inf
```

No `/install`: replacing a driver bound to a running device has bugchecked
this board before. Check that the new package's `DriverVer` is newer than
the installed one (`pnputil /enum-drivers`, look for `rknpu.inf`).

### 2. Mark the device for reinstall, as SYSTEM, and reboot

The Enum key is writable by SYSTEM only. `rknpu-reinstall.ps1` (in the
artifact, from [tools](../tools/rknpu-reinstall.ps1)) sets bit 0x20
(CONFIGFLAG_REINSTALL) in the device's `ConfigFlags` and nothing else. Copy it
to `C:\rknpu\`, then from an administrator prompt:

```
schtasks /create /tn rknpu-reinstall /sc once /st 23:59 /ru SYSTEM /f /tr "powershell -NoProfile -ExecutionPolicy Bypass -File C:\rknpu\rknpu-reinstall.ps1"
schtasks /run /tn rknpu-reinstall
timeout /t 5
type C:\Windows\Temp\rknpu-reinstall.log
schtasks /delete /tn rknpu-reinstall /f
reg query "HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\RKCP3576\0" /v ConfigFlags
shutdown /r /t 0
```

`ConfigFlags` must show bit 0x20 set before the reboot. After it:

```
pnputil /enum-devices /instanceid "ACPI\RKCP3576\0" /drivers
rknputest info
```

`Status: Started` on the new `oem<N>.inf`, and `rknputest info` passes as in
M2 and now prints `m3: version 1, 0 buffers, 0 KiB`. Up to here no job has
run; if anything is wrong already, stop and send this.

### 3. Run it

```
rknputest m3 > m3.txt 2>&1
type m3.txt
reg query "HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\RKCP3576\0\Device Parameters"
rknputest info
```

Expected, with the addresses and timings filled in by the hardware:


(21 jobs a core: four shapes five times, and one after the reset; one
interrupt a task, 146. `raw` may also carry DPU_1, 0x200; any DMA error bit,
0x1000 or 0x2000, fails the job.) Exit status: 0 pass, 3 wrong numbers, 4 a job did not
complete or a reset was not clean, 1 refused or a device error. After a run
the breadcrumbs should read `M3Stage` 9 (the last buffer freed).

**M3 passes** with `RKNPU M3: PASS` and the board still up for a second
`rknputest m3` and `rknputest info` (no unclaimed interrupts) without a
reboot in between.

How to read a failure:

| Output | Reading |
|---|---|
| `did not complete (timed out ...)`, `isr 0` | the interrupt never came: the job did not run, or bypass does not let it reach memory. Was the reset clean, and does a second `rknputest m3 --core 0 --shape 1 64 64 --iters 1` behave the same? |
| `DMA error` | the NPU tried and the bus refused: bypass or address width; M6 before going further |
| `off by the same N` | the arithmetic is right and the output stage adds a constant (charsiu's lift of 128 would show as 128) |
| other wrong words, canary intact | layout or cache attributes; send the dump, change nothing |
| canary words overwritten | the NPU wrote past its output: stop, reboot, send everything |
| a bugcheck | send the minidump and the breadcrumbs (they were flushed before the job started) |

Single shapes for a second look: `rknputest m3 --core 0 --shape M K N` with a
K, N pair from `m3_streams.h` (64 64, 256 64, 256 256, 1024 1024) and
M 1 to 64; `--iters N`; `--map` reads step 1's output through `MAP_BO`;
`--no-reset` skips the reset step.

### 4. Back-out

- Quickest, and it needs no Windows at all: set the firmware option off
  (UEFI shell: `setvar AcpiNpu -guid 8b4f2e3d-ac5e-4f9b-c2d6-3e7e9f1b4d8c -bs -rt -nv =00`,
  then `reset`). The SSDT is not published, the device does not exist, and
  neither driver loads.
- Back to M2: with the firmware option off (above) and Windows booted, the
  device is absent and the M3 package is not in use, so
  `pnputil /delete-driver oem<N>.inf` (the M3 `rknpu.inf`, no `/force`)
  removes it. Turn the option back on and reboot: the device binds the M2
  package, still in the driver store from M2.
- If Windows does not boot after step 2: the same, firmware option off first.

## What to send back

`m3.txt`; the two `rknputest info` outputs (step 2 and step 3); the
`Device Parameters` dump; `pnputil /enum-devices` from step 2; on a bugcheck,
the minidump and the bugcheck code.

## Risks and what is not tested

- **Nothing here has run on hardware.** Not the driver's M3 paths, the
  `_DSM` reset (its first run is here, and it writes the CRU from AML), the
  RK3576 task chaining, or core 1's extra `S_POINTER` bit under Windows.
- **Bypass has never been tested** (M0 not run). See above.
- **Memory mapping, explicitly:**
  - the NPU writes physical memory through any address its stream gives; the
    stream check covers five registers, not all of them, and the canary sees
    only overruns right after an output row, not a write elsewhere;
  - buffers are contiguous and below 4 GiB; on a 4 GB board the space below
    4 GiB is the 3 GiB from 0x40000000, shared with everything else that
    needs low memory, so CREATE_BO can fail (it says so) rather than corrupt;
  - every CPU mapping of a buffer is write-combined (Normal non-cacheable),
    in the kernel and in MAP_BO, so no page is mapped cacheable and
    non-cacheable at once;
  - a MAP_BO mapping is undone in its own process when the handle closes; if
    a duplicated handle outlives that process the buffer is leaked, not
    freed, so no freed page stays mapped in user space. rknputest does not
    map anything unless `--map` is given.
- The medium shape (one task reading 1 MiB of int8 weights) has not been run
  under Linux with `acc_out` either; charsiu runs that size in its runtime
  with int4 and fp16 weights.
- `ExAllocatePool2` needs Windows 10 2004 or later; the INF's floor says
  16299. Only 23H2 is in use.
