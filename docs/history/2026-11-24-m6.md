# M6: the driver owns the NPU IOMMUs

Status: first board run 2026-11-24 (rknpu 3.53.19.189). `rknputest info` is OK
in IOMMU mode with cached buffers; `rknputest m6` gave SCATTER OK, every M3
ladder shape EXACT on both cores through the IOMMU, 0 faults, 0 timeouts. Its
"both cores at once" step failed: the second handle's WRITE_BO came back
ERROR_BUSY (170). The cause was M3's rule that WRITE_BO and MAP_BO wait while
*any* job without RKNPU_SUBMIT_COPY runs. That rule is now scoped to the job's
own handle, which is the only one that can reach those buffers. The host test
(`rknputest-fake m6`, two threads with overlapping jobs) reproduces the board
failure under the old rule, and CI runs it both ways. The fixed build has not
been on the board yet.

Second board run (rknpu 4.7.50.865, BUCK2 800 mV): SCATTER OK (192 x 4 MiB,
197 page-table pages). Both cores now ran at once, but both produced wrong
results (10039 and 8350 of 16384 words), with 0 faults and 0 canaries hit;
one core after the other stayed EXACT. The cause is the hardware, not the
driver: **the two cores share one CBUF**, and two jobs that run together
corrupt each other when their streams use the same CBUF window. charsiu
established this in its rounds 362 and 363 and gives device d window d.
rknputest's captured streams were all window 0. The fix has three parts:

- m3gen now captures every shape in both windows, and core c runs window c.
- SUBMIT reads each job's window (CNA 0x1040). If the other core's running
  job uses the same window, the new job waits for it, so a client can never
  corrupt the other core silently (`cbuf_waits` in GET_INFO).
- `rknputest m6 --collide` puts both cores on window 0 on purpose. It must
  stay exact, at a ratio near 1, with CBUF waits counted.

The fake device models the shared CBUF. Without the driver's wait it
corrupts both jobs, as the board did, and CI checks both outcomes.

M4 ran charsiu on the TaishanPi 3M under Windows and got the CPU arm exact,
but the NPU arm was 3 to 5 times slower than the CPU, and it did not repeat
itself from one run to the next. The board log (`m4-windows2`) says why:

- Every buffer had to be physically contiguous below 4 GiB, because the
  IOMMUs were left in bypass. 4 MiB allocations started failing at 80 to
  370 MiB held ("no contiguous memory below 4 GiB", -12), and each failure
  left a different tensor on the CPU. The text differed run to run, and so
  did the submit count (6484 against 6613).
- The device was exclusive. charsiu's second device would not open
  ("only one NPU file could be opened; the second core stays idle").
- The driver's queue was sequential and WAIT held the job lock while it
  waited. Even with two handles, the cores could not have overlapped.
- Every buffer was write-combined, that is, uncached for the CPU. Reading
  the accumulators back took 83% of the batched prefill path (958 of
  1153 ms).
- Each wait polled about 18 IOCTLs over 206 us and won 1% of the time.

M6 fixes all five. Each fix can be switched off, so the board run can
measure what each one is worth.

## Design

### IOMMU mode (the default)

The IOMMU code is in `drivers/rknpu/iommu.c`. It follows mainline
`rockchip-iommu.c` and its v2 page-table format; the instances are
`rockchip,rk3576-npu-iommu` / `rockchip,rk3568-iommu`.

- **The page table.** There is one page directory and the page tables are
  allocated as needed: 4 KiB pages, 32-bit IOVA, 40-bit physical addresses.
  All four instances (2 per core, at +0x2000 and +0x2100) point at the same
  directory. The tables are write-combined, because the IOMMU walks them
  without snooping. A DSB is all a table write needs before the IOMMU is
  told.
- **Buffers.** A buffer is `MmAllocatePagesForMdlEx` pages, from anywhere
  below 2^40, mapped once at CREATE_BO. Nothing is remapped per submit.
  `dma_address` is the IOVA. IOVAs start at 1 MiB, so no buffer sits at
  IOVA 0.
- **Guard pages.** IOVA is handed out in 64 KiB chunks, and each buffer gets
  at least one unmapped page after its end. An overrun therefore faults
  instead of reaching the next buffer. A chunk table maps each chunk to the
  buffer that owns it.
- **Turning paging on.** SUBMIT turns paging on for the core when it finds
  it off, or pointing at the wrong directory. That costs six register reads
  per job when nothing needs doing. The sequence is rk_iommu_enable(): stall,
  FORCE_RESET with the DTE_ADDR read-back test, DTE_ADDR, ZAP_CACHE,
  interrupt mask, AUTO_GATING bit 31, ENABLE_PAGING, unstall. A core reset
  that takes the IOMMU with it is repaired at the next job. That is the
  Linux series' "MMU_DTE_ADDR is not functioning" recovery, checked on
  every job.
- **Turning paging off.** Paging goes off before a `_DSM` core reset (as
  rocket detaches its domain) and at D0 exit. The firmware and the next OS
  then find what the firmware left.
- **Zaps.** Unmapping zaps every page from every instance. Mapping zaps the
  first and last page, as rk_iommu_map() does.
- **Faults.** A page fault or bus error is acked in the ISR (ZAP_CACHE,
  PAGE_FAULT_DONE, INT_CLEAR) and stops the job with `RKNPU_JOB_MMU_FAULT`.
  WAIT resets the core and returns `fault_addr` and `fault_status`. If an
  instance faults with no job running, it is masked until the next SUBMIT,
  so a fault cannot turn into an interrupt storm.
- **The copy arena.** The arena is mapped read-only for the NPU.
- **Safety model.** The safety model is unchanged:
  - SUBMIT still copies and checks every stream: the allow list, no PC
    block writes, and every address register inside one of the caller's
    buffers.
  - The IOMMU now bounds what the NPU can reach to what the driver mapped.
    The check keeps one handle out of another's buffers, because the table
    is shared.
  - The address lookup is a single chunk-table read instead of a walk over
    about 1300 buffers, and handles go through a hash.
- **Buffer limit.** The limit is 1536 MiB in IOMMU mode, which the int8
  Llama-3.2-1B (1379 MiB) fits.

### Cached buffers and cache maintenance

- **Mappings.** In IOMMU mode the CPU mappings (the driver's and MAP_BO's)
  are cached, as rocket's are.
- **PREP_BO and FINI_BO.** The two reserved codes 0x812 and 0x813 are now
  implemented:
  - FINI_BO cleans the range (`DC CVAC`) before the NPU reads it.
  - PREP_BO cleans and invalidates it (`DC CIVAC`) before the CPU reads what
    the NPU wrote.
  - Both end with `DSB SY`. They are in `drivers/rknpu/cache.asm`, because
    the WDK has no intrinsic for them.
- **WRITE_BO and READ_BO** do the maintenance themselves.
- **New buffers** are cleaned and invalidated at CREATE_BO, so a dirty zero
  line can never land on NPU output later.
- **charsiu needs no change.** It already brackets every CPU access with
  prep and fini for rocket. The port turns those calls into the two IOCTLs
  when `GET_INFO.bo_cached` is set, and they are no-ops otherwise.

### Both cores, interrupt-driven completion

- **More handles.** The device is no longer exclusive, so charsiu opens two
  devices and splits each matmul over both cores. `CHARSIU_NPU_ONEDEV=1` is
  the one-core control.
- **Parallel queue.** The driver queue is parallel.
- **WAIT.** WAIT waits on the core's completion event with no lock held. It
  takes the job lock again only to collect the result, or to stop a job
  that timed out.
- **No polling by default.** The port no longer polls: `CHARSIU_NPU_SPIN_US`
  now defaults to 0. A blocking WAIT is woken by the job's interrupt (ISR,
  then DPC, then event), so each submit costs one SUBMIT and one WAIT.
- **Chaining tasks.** Tasks within a job are already chained from the ISR:
  the next task starts in the interrupt, with no trip back to user mode.

### The shared CBUF

The cores share one CBUF. Two jobs that run at once must use different CBUF
windows, or both come out wrong. Window 0 has CNA 0x1040 = 0x10000000 and
window 1 has 0x2c001c00 (charsiu `src/job.c`, `charsiu_job.cbuf_window`).

The driver computes each job's key from its checked (copied) streams with
`rknpu_rc_cbuf_key()`. A stream with no 0x1040, or a job whose tasks
disagree, counts as colliding with everything. When the key collides with
the other core's running job, SUBMIT waits for that job, for at most
RKNPU_WAIT_MAX_MS, then returns busy.

charsiu's two devices use windows 0 and 1, so they never wait. In the host
model of a Llama run, 261 of 746 SUBMITs overlapped the other core's job,
0 of them on the same window. charsiu itself serialises its batched
(prefill) submits by default because of a separate two-core issue it has
not explained (`CHARSIU_NPU_BATCH_PARALLEL`, npudev.c). Decode (m = 1)
overlaps.

### What was not done, and why

- **A boot-time reserved contiguous pool (step 2 of the plan).** Not built.
  It would only be needed if the IOMMU turned out infeasible, and nothing
  found here says it is:
  - The registers are in the window the SSDT already gives the driver.
  - The interrupts are the cores' lines, which the ISR already reads.
  - Every clock and power domain the IOMMU node lists in rk3576.dtsi
    (aclk_rknn0/1, hclk_rknn_root, clk_rknn_dsu0, aclk/hclk_rknn_cbuf,
    PD_NPU0/1) is one Npu.c already turns on.
  - A pool would also keep both of M4's limits: it is below 4 GiB, and it
    takes memory away from Windows for the whole boot.
  - If the board shows the IOMMU cannot be made to work, the pool is the
    fallback. It would be an ACPI-described reserved region, and the
    allocator would replace the contiguous calls in bypass mode.
- **Hardware task chaining (TASK_NUMBER > 1 in a single PC launch).** Not
  done. The vendor driver does this with a 4-entry trailer
  (`RKNPU_PC_DATA_EXTRA_AMOUNT`) that its compiler appends to each stream.
  That trailer's RK3576 content has not been captured, and rocket and Mesa
  run one task per launch. The vendor kernel's `trailer_dump` instrument
  can capture it; until then, the per-task cost stays at one interrupt.
- **A larger SUBMIT.** `RKNPU_MAX_TASKS` and the 256 KiB arena stay as they
  are. The M4 run split none of its 6484 SUBMITs (5.3 tasks each, at most
  18944 bytes of stream). Raising the limit would change the layout and gain
  nothing.
- **Firmware.** Nothing is needed for M6, so there is no new edk2 branch.

### Switches (Device Parameters, read when the device starts)

| value | effect |
|---|---|
| none (default) | IOMMU mode, cached buffers |
| `M6CachedBos = 0` | IOMMU mode, write-combined buffers (measures what caching is worth) |
| `M6Iommu = 0` | M4's bypass mode exactly: contiguous below 4 GiB, write-combined |
| `M4AllowUnlisted = 1` | as in M4 |

The key is `HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\RKCP3576\0\Device Parameters`.
It is writable by SYSTEM only. Set a value through a SYSTEM scheduled task, as
with `rknpu-reinstall.ps1`, then disable and enable the device or reboot.

## Board test, one install

You need two artifacts from the same CI run: `rknpu-m6-arm64` (driver,
`rknputest.exe`, `signer.cer`, `rknpu-reinstall.ps1`) and `charsiu-m6-arm64`
(`charsiu_run.exe`, `win-bench.ps1`, `long.txt`). Unpack both into
`C:\rknpu`. The model stays at `R:\npu\Llama-3.2-1B-Instruct-Q8_0.gguf`
(unsloth, sha256 3f87a880...). Turn minidumps on, as for M3 and M4.

**1. Stage the driver.** As administrator, after `w32tm /resync /force`:

```
certutil -addstore -f Root C:\rknpu\signer.cer
certutil -addstore -f TrustedPublisher C:\rknpu\signer.cer
pnputil /add-driver C:\rknpu\rknpu\rknpu.inf
```

This only stages the package; there is no `/install`.

**2. Mark the device for reinstall, as SYSTEM, then reboot:**

```
schtasks /create /tn rknpu-reinstall /sc once /st 23:59 /ru SYSTEM /f /tr "powershell -NoProfile -ExecutionPolicy Bypass -File C:\rknpu\rknpu-reinstall.ps1"
schtasks /run /tn rknpu-reinstall
type C:\Windows\Temp\rknpu-reinstall.log
schtasks /delete /tn rknpu-reinstall /f
shutdown /r /t 0
```

**3. Check the binding, then run the benchmark.** First, check which driver
is bound:

```
pnputil /enum-devices /instanceid "ACPI\RKCP3576\0" /drivers
C:\rknpu\rknputest.exe info
```

`rknputest info` must print `m6: version 1, memory IOMMU (driver page table),
buffers cached` and `RKNPU INFO: OK`.

Then run the benchmark as a SYSTEM task, so a dropped ssh session cannot
stop it:

```
schtasks /create /tn rknpu-m6 /sc once /st 23:59 /ru SYSTEM /f /tr "powershell -NoProfile -ExecutionPolicy Bypass -File C:\rknpu\win-bench.ps1 -Model R:\npu\Llama-3.2-1B-Instruct-Q8_0.gguf -Out R:\npu\m6-windows"
schtasks /run /tn rknpu-m6
```

When it finishes, `R:\npu\m6-windows.zip` exists and `bench.txt` inside it
is the summary. Add `-Linux R:\npu\m4-linux` once `tools/m4/linux-ref.sh`
has been run under Armbian, to compare against the Linux text and tokens/s.

**Optional follow-ups:**

- Run `-IdleDisable` once: it disables processor idle for the arms, the
  counterpart of charsiu's `/dev/cpu_dma_latency` hold on Linux.
- Set `M6CachedBos = 0`, reboot, and run `-Quick`, to price caching.

## What confirms each step

| step | evidence in the zip | confirms it when |
|---|---|---|
| IOMMU mapping works | `m3.txt` | `RKNPU M3: PASS`, every shape EXACT, the buffers printed as IOVAs (0x001.....) |
| contiguous limit gone | `m6.txt` | `SCATTER OK`: 192 of 192 4 MiB buffers (M4 failed from 80 MiB); in the charsiu arms, `fallbacks` 0 and no "rknpu buffer of ... failed" |
| determinism | `bench.txt` | `short-npu and short-npu2: SAME TEXT`, and equal `submits` |
| fault handling | `m6.txt` | `IOMMU FAULT as intended` at an address 128 bytes before a 4 KiB boundary plus the guard page, then the same core EXACT again; `info-after` shows the faults counted and no other errors |
| per-job cost | `m6.txt` | `LATENCY:` average SUBMIT-to-WAIT for the one-task job. M4's charsiu model read 97 us per call plus 80 us per task, and the M3 test measured about 130 us |
| both cores | `m6.txt`, `bench.txt` | `PARALLEL:` near 2x; `short-npu` has `npu_devices` 2 and decodes faster than `short-npu1` |
| cached buffers | `bench.txt`, `.err` | `syncs` above 0, no "PREP_BO/FINI_BO failed", and the same text as before; against an `M6CachedBos = 0` run, the prefill "read" line in `short-npu.err` falls well under M4's 958 ms |
| end result | `bench.txt` | `decode: NPU x tok/s vs CPU y tok/s` above 1x (M4: 0.85 against 2.88). The Linux reference for a similar 1.1B model is 21.88 tok/s |

If decode is still below the CPU with `fallbacks` 0 and `npu_share_pct`
small, the time is outside the NPU. Check `page_faults` and `peak_ws_mib`
against the CPU arm (paging the model back in from the USB stick), and read
the `stages` arm, which is `CHARSIU_STAGES=1` (where a token goes).

## Backing out

- **Bypass mode.** Set `M6Iommu = 0` (as SYSTEM) and reboot. The driver is
  then M4's in everything but the parallel queue and the non-exclusive open.
- **The M4 package.** Stage the M4 package and repeat step 2.
- **A bugcheck at boot.** Turn the firmware's NPU option off; the device
  then never enumerates.
