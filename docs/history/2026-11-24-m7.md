# M7: decode performance, Windows against Linux

M6 decodes Llama-3.2-1B-Instruct (unsloth Q8_0, sha256 3f87a880..., charsiu
w4a16, NPU 594 MHz, TaishanPi 3M) at **12.12 tok/s, 82.5 ms a token**.
charsiu on mainline Linux (rocket), same board class, same NPU clock, CPU
pinned at maximum and held out of deep idle, decodes the same model at
**18.15 tok/s, 55.1 ms a token** (charsiu `docs/paper-evidence.md`, section
1). Windows is at 67% of Linux. M7 is the attribution of the 27.4 ms and the
fixes that belong to this repository (driver and port), each behind a switch,
plus a benchmark that measures each one on the board.

Nothing in M7 changes a number charsiu computes: every M7 NPU arm must print
the same text, and `m7-bench.ps1` checks that it does.

## Where the M6 token goes

From the M6 board run (`npu-m6-2026-11-24/m6-windows.zip`, rknpu 3.53.19.189):
`short-npu.err` (128 tokens, both cores) and the `stages` arm
(`CHARSIU_STAGES=1`, 32 tokens). Per generated token; charsiu's batched
prompt entry is subtracted where charsiu prints it separately.

```
  a decode token, M6 (short-npu)                          ms
  ---------------------------------------------------- -----
  NPU busy, per core (driver hw_us, T0 to the last IRQ)  ~34   (36.3 incl. prompt)
  65 matmul calls (charsiu's "hardware path")            62.7
     submitting (2 SUBMIT IOCTLs a call, ~95 us each)    12.3
     fence (WAIT + PREP_BO; the NPU's time is in here)   37.0
     reading the accumulators back                        8.0
  packing the activations (FINI_BO IOCTLs inside)         4.5
  everything else on the CPU (attention, silu * up,      15.3
     norms, rope, embedding, sampling)
  ---------------------------------------------------- -----
  total                                                  82.5

  IOCTLs a decode call: 10  (FINI in x2, SUBMIT x2, WAIT x2, PREP out x2, FINI out x2)
  IOCTLs a token: ~650; PREP_BO + FINI_BO alone 380 a token, 22 us each, 8.4 ms,
  of which the cache maintenance itself is ~0.3 ms (4.6 MB a token cleaned or
  invalidated, at charsiu's 13.8 GB/s): the rest is the IOCTL.
```

The stage table (second half of the `stages` arm, 75.7 ms a token):
`gate + up` 22.94, `down` 16.60, `output head` 10.60, `q k v` 9.55,
`o proj` 5.30, `attention` 5.96, `silu * up` 3.06, `token embedding` 0.65,
the rest under 0.4 each. The first half is 94.6 ms: first-touch page faults
(`rope + kv copy` 4.23 against 0.35, `token embedding` 2.23 against 0.65).

The NPU hardware is not where Windows loses: 309 MB of int4 weights a core a
token in ~34 ms of busy time is ~9 GB/s a core, the same marginal rate
charsiu's Linux fits give (about 115 us a MB on the busier core). It is the
same silicon, clock and IOMMU, so Linux spends about the same ~34 ms with the
NPU busy. **The gap is the time the NPU sits idle between jobs: ~48 ms a
token on Windows against ~21 ms on Linux.**

## The gap, ranked

| # | cause | Windows | Linux | gap, ms a token | basis |
|---|---|---|---|---|---|
| 1 | CPU work runs slower: the decode thread is not pinned to the A72s, the pool barrier is slow, and the CPU clock is lower | 27.8 ms of CPU work a token (15.3 stages + 8.0 read + 4.5 pack) | same code, pinned A72 at 2208 MHz | **~12** | charsiu pins by reading sysfs, which Windows lacks, so the thread was a lottery (charsiu measured +26% decode when it lands on an A53); MADT EfficiencyClass is 0 on every core, so Windows cannot tell the clusters apart; `silu * up` (16 barriers, 1.4 ms of work at charsiu's 10.4 ns an element) took 3.06 ms, ~170 us a barrier against the 50 us charsiu's pool sizing assumes; TSPI firmware default CPU clock 1608 MHz against 2208 (x1.37) |
| 2 | SUBMIT IOCTL cost, serial on the decode thread | 2 x ~95 us a call, 12.3 ms | rocket's whole per-call fixed cost is 43 to 51 us (charsiu's three-term fits) | **~9** | the second core also starts one SUBMIT later than the first, every call; the stream copy and check is **not** the cost: 0.83 us for a 148-entry w4a16 stream on the host, a few us on the A72 |
| 3 | PREP_BO / FINI_BO one IOCTL each | 380 a token, 8.4 ms (~6.5 on the critical path; the first core's PREP overlaps the second core's job) | rocket's ioctls are a few us | **~6** | the cache maintenance is ~0.3 ms of it |
| 4 | interrupt to waiter, and the WAIT IOCTL | fence minus NPU busy, ~3 ms (~50 us a call incl. one PREP) | threaded IRQ plus dma_fence wake | **~1 to 2** | not split on M6; M7's `irq_dpc_us` and `dpc_wake_us` measure it |
| 5 | deep idle (charsiu's `/dev/cpu_dma_latency` hold, worth 24% on Linux) | the open failed (`No such file`), but this firmware has no `_LPI` unless "CPU Idle States" is enabled in setup, so Windows idles in WFI only | 100 us bound: WFI allowed, CPU_SLEEP not | **~0** expected | the `short-idle` arm (idle disabled outright) is the control |
| 6 | the NPU itself | ~34 ms busy a core | the same | **0** | see above |

Rows 1 to 4 sum to about 28 ms against the 27.4 measured; each is an estimate
from the M6 counters, and the M7 bench measures each one directly.

**Not decode, but the biggest wall-clock item:** staging is 75 to 99 s a run,
61 s of it quantising Q8_0 to int4 on the CPU at every start (charsiu measures
about 10 s for this on Linux), and ~500k page faults, which are mostly the
1.3 GB gguf mapped and read once. charsiu already has the fix: the weight
cache, `charsiu_run --cache` (a sidecar of the quantised weights beside the
model, keyed by the model's size and mtime and by the quantiser's version).
The M6 bench never passed it.

## What M7 changes

| change | where | default | switch (control) | targets |
|---|---|---|---|---|
| FINI_BO deferred to the device's next SUBMIT (`RKNPU_SUBMIT_CLEAN`), PREP_BO done by the job's WAIT (`RKNPU_WAIT_PREP`): a decode call is 4 IOCTLs instead of 10 | driver + port | on with an M7 driver | `CHARSIU_RKNPU_FUSE=0` | row 3 |
| WAIT without the three diagnostic register reads after a clean finish (`RKNPU_WAIT_LEAN`) | driver + port | on | (part of the M7 WAIT) | row 4 |
| the DPC wakes the waiter with a priority boost (`EVENT_INCREMENT`) | driver | on | `Device Parameters\M7WakeBoost = 0` (read at start) | row 4 |
| the driver reports its own SUBMIT time (`drv_us`), the interrupt-to-DPC and DPC-to-waiter times | driver + port | on | none needed | rows 2, 4: measurement |
| charsiu's CPU pinning works: the sysfs files it reads are answered from Windows (EfficiencyClass, else the core type in MIDR_EL1, else the clock) | port (compat) | on | `CHARSIU_WIN_SYSFS=0` | row 1 |
| mutexes and condition variables as SRW locks with a 50 us spin before sleeping | port (compat) | on | `CHARSIU_WIN_SYNC=pthread`, `CHARSIU_WIN_SPIN_US=0` | row 1 |
| charsiu's CPU hold: power throttling off (no EcoQoS) and a 1 ms timer for the process; prints how many idle states Windows has | port (compat) | on | `CHARSIU_NPU_IDLE=1` (charsiu's own), `CHARSIU_RKNPU_QOS=0` | row 5 |
| each device's SUBMIT on a thread of its own, so a call's two SUBMITs overlap | port | **off** | `CHARSIU_RKNPU_ASYNC=1` turns it on | row 2 |
| cache maintenance in the process (DC CVAC / DC CIVAC by VA), if a probe shows user mode may (SCTLR_EL1.UCI) | port | **off** | `CHARSIU_RKNPU_UCACHE=1` turns it on | row 3 |
| the weight cache | bench | on from the second arm | the `short-m6` arm runs without it | staging |

Off by default, and why: `ASYNC` moves a SUBMIT failure from
`charsiu_submit_jobs` to the next PREP (whose result charsiu's decode path
does not check) and every later SUBMIT, and its thread spins on one CPU
while the NPU decodes; `UCACHE` depends on what the kernel allows user mode,
and a wrong answer there is silently stale data, so it needs the bench's text
check on the board before it can be a default.

**Considered and not done:**

- **A cache of validated streams** (skip the copy and the check when a
  stream has not changed): the check measured 0.83 us for a real 148-entry
  w4a16 stream on the host, a few us on the A72, against ~95 us a SUBMIT.
  `drv_us` will say whether the driver's part of SUBMIT is worth more work.
- **Large pages for the gguf, or prefetching it:** the page faults are in
  staging, which the weight cache removes after the first run; a file
  mapping cannot use large pages on Windows.
- **A PoFx or power-setting idle limit from the driver:** Windows has no
  per-process or per-device CPU idle-latency bound without a PEP, and with no
  `_LPI` there is nothing deeper than WFI to forbid. A power-scheme change
  (`PowerSetActiveScheme`) is system state and is kept as a bench control
  only (`short-idle`).
- **Batching a token's calls into fewer SUBMITs:** charsiu already groups
  q/k/v and gate/up and issues one SUBMIT a device a call; fewer would need
  charsiu's graph to change, and the layers depend on each other.

**Firmware, not in this repository** (edk2-rk3576), and worth knowing when
reading the numbers: the TSPI CPU clock defaults to 1608 MHz ("CPU Maximum
Frequency", branch cpu-idle-dvfs); the MADT leaves EfficiencyClass 0 on every
core, so Windows' scheduler treats the A53s and A72s as equal (the port's
pinning works around it for charsiu); "CPU Idle States" (`_LPI`) is off by
default.

## Host checks

- `make -C port check` and `devtest` in every mode CI runs: M7, M6, M4,
  `FUSE=0`, `ASYNC`, `UCACHE` and their mixes. The in-memory driver applies
  the clean list before it looks for streams written since their last FINI,
  so a deferred clean that never arrived fails the test.
- ThreadSanitizer on the `ASYNC` path: clean.
- `charsiu_run` on the in-memory driver with a real Llama-3.2-1B gguf: the
  same output with M6, M7, `ASYNC` and `UCACHE`; on M7, 2512 FINIs rode on
  SUBMITs and 1266 PREPs on WAITs, 34 FINI_BO IOCTLs were left (staging), and
  0 jobs ran from unflushed streams.
- The Windows binaries build with llvm-mingw 20261020; the compat wrappers
  cannot run on the host (no Windows), so the board run is their test.

## Board test

You need two artifacts from the same CI run: `rknpu-m7-arm64` (driver,
`rknputest.exe`, `signer.cer`, `rknpu-reinstall.ps1`) and `charsiu-m7-arm64`
(`charsiu_run.exe`, `m7-bench.ps1`, `long.txt`). Unpack both into
`R:\npu\m7` (C: has about 1 GB free). The model stays at
`R:\npu\Llama-3.2-1B-Instruct-Q8_0.gguf`. Minidumps on, as before.

**1. Install the driver** exactly as M6 (docs/M6.md, steps 1 and 2), from
`R:\npu\m7`: `certutil` the signer into Root and TrustedPublisher,
`pnputil /add-driver R:\npu\m7\rknpu\rknpu.inf`, the SYSTEM task with
`rknpu-reinstall.ps1`, reboot.

**2. Check the binding:**

```
pnputil /enum-devices /instanceid "ACPI\RKCP3576\0" /drivers
R:\npu\m7\rknputest.exe info
```

The driver version is the CI run's DriverVer, and `rknputest info` prints
`m6: version 1, memory IOMMU (driver page table), buffers cached`.

**3. Run the bench as SYSTEM** (about 20 minutes; staging is ~90 s for the
two arms without the weight cache and ~10 s for the rest):

```
schtasks /create /tn rknpu-m7 /sc once /st 23:59 /ru SYSTEM /f /tr "powershell -NoProfile -ExecutionPolicy Bypass -File R:\npu\m7\m7-bench.ps1 -Model R:\npu\Llama-3.2-1B-Instruct-Q8_0.gguf -Out R:\npu\m7-windows"
schtasks /run /tn rknpu-m7
```

`R:\npu\m7-windows.zip` appears at the end; `bench.txt` and `decode.txt` are
the summary. The `short-idle` arm inside it is the idle control: it sets the
processor idle-disable power setting for that arm only and restores it.

**4. The whole-run idle control** (optional, a second run): the same task
with `-IdleDisable -Quick -Out R:\npu\m7-idle`, which disables processor idle
for every arm.

**5. The wake boost** (optional): set `M7WakeBoost = 0` as SYSTEM, reboot,
and run `-Quick -Out R:\npu\m7-noboost`; then delete the value and reboot.

**What confirms it:**

| question | where | answer |
|---|---|---|
| M7 changed no number | `bench.txt` | `TEXT: all N short-npu arms print the same text`, and the same for `stages` and `long-npu`. Anything else: stop, send the zip |
| the fused path is on | `short-npu2.err` | `charsiu rknpu: M7 driver; cache maintenance fused into SUBMIT and WAIT`; in `decode.txt`, "PREP/FINI IOCTLs left" near 0 and "IOCTLs a token" ~260 (M6: ~650) |
| pinning works | `short-npu2.err`, `decode.txt` | `this thread on the fastest cluster, 4 CPUs`, and "decode thread pinned" True; False in `short-nopin` |
| what each change is worth | `bench.txt` | the per-arm lines against `short-npu2` |
| what is left in SUBMIT | `decode.txt` | "one SUBMIT, us" against "of which the driver": a small driver share means the time is Windows' IOCTL path, which only fewer IOCTLs (`ASYNC`, fusing) can cut. `drv_us` includes any wait for the other core on the same CBUF window (01730b2); charsiu's two devices use two windows, so the driver's `cbuf_waits` counter (rknpu_core_info, printed in `m6.txt`'s core totals) should grow only during the m6 test, not during the charsiu arms |
| the interrupt path | `decode.txt` | "interrupt to DPC" and "DPC to the waiter running" |
| the weight cache | `bench.txt` | the staging line: `short-m6` (none), `short-npu` (writing), `short-npu2` (reading) |
| against Linux | `bench.txt` | `decode: M7 x tok/s ... N% of Linux` |

## Backing out

Every port change has its environment switch above; `short-m6` runs all of
them off at once. The driver's M7 paths are only taken when the caller asks
for them (an M6 `charsiu_run.exe` runs unchanged on the M7 driver), and
`M7WakeBoost = 0` restores M6's wake. To go back entirely, stage the M6
package and repeat the reinstall.
